# Автоматический обмен с ERP

## Статус работ

По решению пользователя от 6 октября 2026 года обследование ERP, проверки подключений и обмена отложены до этапа интеграции. Доступная ERP — стандартная облачная база без игровых доработок. Этот документ описывает целевой обмен; возможности текущей базы ещё не проверены. Ближайшая разработка логики и интерфейса Элемента выполняется на тестовых данных по [плану реализации](implementation.md).

## Принятое требование и выбор транспорта

Обмен должен быть автоматическим. Пользователь предложил рассмотреть OData. Протокол не закрепляется в модели игры: сервер получает нормализованные снимки ERP и отправляет именованные команды с устойчивыми идентификаторами.

Стандартный интерфейс платформы 1С:Предприятие использует **OData 3.0**, поддерживает чтение, создание, изменение объектов и проведение отдельных документов. Возможности опубликованной конкретной базы определяются её метаданными и правами. [Официальное описание 1С](https://v8.1c.ru/platforma/rest-interfeys/).

Рекомендуется сначала проверить гибридный вариант. OData использовать для чтения опубликованных данных; согласованные игровые снимки, фиксацию фазы и составные операции выполнять через адаптер ERP. Возможность использовать только OData проверяется отдельным техническим прототипом.

| Вариант | Чтение | Команды | Условия применения |
|---|---|---|---|
| Прикладной HTTP API | Адаптер возвращает единый снимок | Адаптер выполняет именованную операцию | Можно установить игровое расширение; протокол независим от метаданных ERP |
| OData | Стандартные сущности и виртуальные таблицы, если опубликованы | Создание/изменение документов и доступные действия | Подтверждены необходимые реквизиты, правила заполнения, фиксация и повторы |
| Гибридный | OData для чтения и мониторинга | Прикладной адаптер для игровых действий | Предлагаемый исходный вариант для обследования |

Сам по себе OData не задаёт смысл команды «подготовить игру» или «оплатить реализацию», не подтверждает согласованность нескольких чтений и не определяет ключ повторного выполнения. Это требования нашего приложения, которые должны обеспечиваться адаптером либо проверенным способом работы с ERP.

Вариант только OData может включать небольшое расширение ERP: сохраняемые интеграционные команды и снимки публикуются через OData, а обработчик ERP выполняет бизнес-операции. Тогда собственного HTTP-сервиса в ERP не требуется. Это отличается от прямой записи типовых документов без адаптера.

## Нормализованный шлюз

`ШлюзERP` реализуется как контракт сервиса Элемента с несколькими транспортными реализациями. Он имеет логические операции:

- Проверить подключение и вернуть перечень поддерживаемых возможностей.
- Прочитать номенклатуру и соответствия.
- Запросить фиксацию фазы и получить согласованный снимок.
- Доставить команду и получить подтверждение исполнения.
- Прочитать фактические продажи и платежи.
- Получить итог после закрытия игрового месяца.

Наличие транспорта не означает поддержку всех операций. Возможности `consistentSnapshot`, `phaseGuard`, `idempotentCommands`, `salesFacts`, `finalFinancials` проверяются при подготовке игры. Отсутствие обязательной возможности показывается ведущему до старта.

## Направление соединения

Для прикладного HTTP-режима предлагается инициатор соединения **ERP**:

1. Адаптер каждой базы опрашивает Элемент и получает команды своего участника.
2. Исполняет команду в локальной игровой области ERP.
3. Передаёт снимки, готовность и подтверждения обратно в Элемент.

Так база ERP не требует входящей публикации собственного HTTP-сервиса. Интервал опроса и повторов задаётся настройками адаптера; он не создаётся как автоматизация чата Codex.

Для прямого OData инициатор — сервер Элемента. ERP должна иметь доступную ему HTTPS-публикацию. Проверить это нужно из серверного окружения Элемента, а не только из браузера ведущего. В гибридном режиме оба канала могут сосуществовать: OData для обычного чтения, исходящий адаптер ERP для согласованных снимков и команд.

## Обследование OData

Первая проверка — чтение документа метаданных:

```http
GET <публикация-ERP>/odata/standard.odata/$metadata
```

Адрес дан как типовой шаблон; реальную публикацию нужно получить у администратора ERP. Имена `EntitySet`, полей, табличных частей и действий берутся из ответа `$metadata`, а не из предположений по русским названиям форм.

Проверить:

1. Версию платформы 8.3, релиз ERP и особенности конфигурации «ДвижжОК».
2. Номенклатуру, характеристики, единицы, виды цен, склады, организации, покупателя, поставщика, соглашения и счета.
3. Источники цен, свободных остатков и денежных остатков; наличие нужных виртуальных таблиц.
4. Возможность получить результат закрытия месяца, прибыль и задолженность. Сохранённые документы не подменяют расчёт фактической себестоимости.
5. Форматы дат, GUID, чисел и ответов; фильтры и пагинацию. Клиент не предполагает формат OData 4.
6. Создание и проведение тестового заказа с нужными реквизитами. Способ автоматического заполнения документа изучается по реальной конфигурации.
7. Поведение при повторе после потери ответа, частичном успехе, изменении данных и ошибке проведения.
8. Возможность запретить игровые изменения во время снимка и получить все показатели в одном согласованном состоянии.

Не предполагаются неподтверждённые гарантии `$batch`, общая транзакция нескольких HTTP-запросов или поддержка условной записи. Возможные механизмы версий данных исследуются на выбранной платформе.

## Соответствия

Игровой код CityRide не считается GUID номенклатуры. Для каждого подключения сохраняется соответствие игрового кода и объекта ERP, при необходимости с характеристикой. Также задаются конкретные организация, склад готовой продукции, кладовая, виды цен, соглашение и счета.

Количество в интерфейсе рынка — штуки велосипедов. Колёса в ERP могут быть штуками или комплектами; коэффициент пересчёта обязателен. В исходных таблицах есть разные модели BOM, поэтому не следует загружать номенклатуру из нескольких файлов без выбранного профиля.

Точные имена сущностей и полей ERP будут оформлены отдельным профилем сопоставления после обследования. В проекте нет вымышленных рабочих URL, учётных записей или GUID ERP.

## Согласованные снимки

Снимок содержит игру, участника, раунд, токен фазы, идентификатор сообщения, версию источника, время данных, предложения и финансовые показатели, если они требуются текущей операцией.

Цена и доступный остаток должны относиться к одной фиксации. Несколько OData GET подряд не доказывают это. Возможные способы:

- ERP фиксирует игровую область и сохраняет полный снимок в интеграционном объекте, который затем читается по HTTP или OData.
- Для проверенной конфигурации запрещаются изменения, собираются данные и проверяется версия до/после. Применимость такого способа нужно доказать на стенде, включая фоновые операции.

Предварительные данные для экрана ведущего могут обновляться периодически, но не используются вместо окончательного снимка. Экран показывает время последнего чтения. Устаревшие данные не дают автоматического подтверждения готовности.

Если данных одной команды нет, расчет по устаревшему состоянию не выполняется. Ведущий либо ждёт восстановление, либо явно исключает команду из раунда до фиксации. Исключение, причина и перерасчёт состава сохраняются в журнале.

## Логические команды ERP

| Команда | Действие адаптера | Критерий успеха |
|---|---|---|
| ПодготовитьИгру | Применить одинаковые стартовые ресурсы и параметры в изолированной области | Контрольный начальный снимок совпал с заданием |
| ОткрытьФазу | Разрешить предусмотренные сценарием действия | Новая версия и токен применены |
| ЗафиксироватьФазу | Ограничить изменения и сохранить снимок | Получен снимок под заданным токеном |
| СоздатьЗаказКлиента | Создать заказ из строк расчёта рынка | Сохранён GUID заказа и игровой ИдОперации |
| ОплатитьРеализацию | Оформить поступление денег за фактически проведённую реализацию | GUID платёжного документа и подтверждённый факт оплаты |
| ЗапроситьИтог | Проверить закрытие месяца и вернуть деньги, прибыль и долги | Получен полный финальный снимок |
| Приостановить / Возобновить | Применить ограничения игрового режима | Подтверждено состояние ERP |

Команда оплаты не создаёт деньги по расчётному заказу, пока нет фактической реализации. Закупки, производство и отгрузки в базовом учебном сценарии выполняются студентами. Настройки будущей автоматизации отдельных учебных действий не смешиваются с транспортным обменом.

## HTTP-контракт адаптера

Для сервиса Элемента предлагается `КорневойUrl: /game/v1`. Платформа добавляет `/api`; полный путь маршрутов — `/api/game/v1/...`.

Формальное описание: [game-api.openapi.json](../contracts/game-api.openapi.json). Оно относится к нашему прикладному API, а не к OData.

| Метод и маршрут после корня | Назначение |
|---|---|
| GET `/bindings/{bindingId}/context` | Разрешённый контекст игры и возможности обмена |
| POST `/bindings/{bindingId}/snapshots` | Согласованный снимок ERP |
| POST `/bindings/{bindingId}/readiness` | Готовность с привязкой к принятому снимку |
| GET `/bindings/{bindingId}/commands` | Очередные неподтверждённые команды в порядке последовательности |
| POST `/bindings/{bindingId}/commands/{commandId}/receipt` | Результат исполнения команды |
| POST `/bindings/{bindingId}/sales-events` | Фактическая реализация и данные связанных платежей |

`bindingId` — привязка сервисного пользователя к участнику. Он не даёт права на чужую игру. Сервер сверяет каждый маршрут с аутентифицированным пользователем.

## Повторы и сбои

- Каждое POST-сообщение имеет `messageId` и `Idempotency-Key` с тем же значением. Ключ действует в рамках подключения, включая маршрут.
- Повтор идентичного запроса возвращает прежний результат. Тот же ключ с другим телом или маршрутом — `409`.
- Очередь выдаёт команды до подтверждения; параметр `afterSequence` — только удобство опроса, не подтверждение выполнения. ERP не пропускает неподтверждённую предыдущую команду.
- ERP сохраняет `commandId` и созданные документы в собственном журнале. Потеря ответа не является основанием создать второй заказ.
- Долгая операция сообщает промежуточное состояние. Факт получения команды отличается от факта завершения.
- Получение запоздалого подтверждения сверяется с исходной командой и её токеном; его нельзя ошибочно отклонить только потому, что сервер уже начал следующий переход. Выполнение новой команды со старым токеном запрещено.
- Для составной операции фиксируется результат каждого шага. Повтор продолжает её с места остановки либо возвращает сохранённый результат.
- Сетевая ошибка повторяется с задержкой. Ошибка обязательных реквизитов ожидает исправления; бесконечные быстрые повторы не выполняются.
- Элемент не отменяет в ERP уже проведённый документ удалением своей команды. Исправление — отдельная операция с причиной и проверкой последствий.

## Финальная сверка

Перед закрытием раунда сверяются заказ рынка, заказ ERP, фактические строки реализации, поступления денег, свободные остатки и задолженность. Допускается частичная отгрузка: она уменьшает фактическую выручку, не превращая весь расчётный заказ в продажу.

Для каждого события реализации передаётся состояние документа с возрастающей версией и список связанных платежей. Один и тот же платёж не суммируется второй раз. Итоговый денежный остаток читается отдельно из ERP: он не вычисляется в Элементе только по событиям продаж.

## Ограничение учебных действий

Фаза, её токен и срок должны проверяться серверными обработчиками ERP при записи игровых объектов, включая запись через OData. Скрытая кнопка в форме не обеспечивает ограничение. Нужные события и исключения для интеграционных и регламентных операций определяются после обследования конфигурации.

Пауза в Элементе немедленно прекращает выдачу новых учебных заданий, но считается применённой в ERP только после подтверждения адаптера. До этого пульт показывает ожидание. При длительной потере связи адаптер переводит игровую область в безопасное ожидание по согласованному правилу, чтобы команда не продолжала менять данные под устаревшей фазой.

## Доступ и секреты

Все соединения используют HTTPS. Для Элемента используется штатная серверная аутентификация выбранной сборки, без собственного генератора токенов. Для OData применяется разрешённая аутентификация публикации ERP с минимальными правами служебного пользователя.

Адрес подключения и ссылка на секрет — настройки среды, секреты не коммитятся. Механизм безопасного хранения секрета и серверной аутентификации проверяется на стенде до реализации. Журнал обмена не сохраняет заголовки авторизации.

Права интеграционного пользователя ограничены конкретной игровой областью. Если команды работают в одной общей базе, одной фильтрации по организации может быть недостаточно; изоляция проверяется на уровне документов, складов, цен и прав. Для первого стенда предлагаются отдельные базы из одного шаблона.
