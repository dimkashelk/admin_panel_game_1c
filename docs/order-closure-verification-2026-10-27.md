# Закрытие заказа и банковская оплата через OData, 27.10.2026

Игрок отгружает все позиции в ERP, затем выбирает заказ в ЛК и нажимает
«Закрыть заказ». Приложение проверяет принадлежность заказа, текущий раунд,
токен и открытые продажи. Короткая транзакция резервирует попытку; сетевые
вызовы выполняются после её завершения.

Проверяются сохранённый GUID/маркер заказа, организация, исходные товары,
количества, цены и сумма. Полная отгрузка подтверждается проведёнными
реализациями, ссылками их строк на конкретный заказ и реальными расходными
движениями `ТоварыНаСкладах`. Количества, характеристики, склады и сумма всех
отгрузок должны совпадать с заказом. Поддерживается подготовленный профиль
`BICYCLE_SIMPLE` со складами без ордерной схемы: реализация сама списывает товар.
Накладная без подтверждённого складского расхода не считается отгрузкой.

До первой записи проверяются банковский счёт, статья ДДС и созданные ERP
объекты расчётов. Поддержаны расчёты по заказу и по нескольким накладным.
Уже существующая другая проведённая оплата по заказу/его объектам расчётов
блокирует автоматическое второе поступление и требует сверки.

Заказ переводится в `Закрыт` с `If-Match` по прочитанному `DataVersion`, затем
повторно проводится. Создаётся `ПоступлениеБезналичныхДенежныхСредств`:
операция `ПоступлениеОплатыОтКлиента`, банковский счёт организации, статья
`ПоступлениеОплатыОтКлиента`, полная сумма и расшифровка по объектам расчётов,
основание — заказ. `ПроведеноБанком=true`; банковская дата и дата входящего
документа передаются с нулевым временем, как их сохраняет целевая ERP.
Дата документа — игровой день, 18:00.

Проведение выполняется `Post()`, без присваивания `Posted` и без режима
загрузки. Затем читаются документ и его конкретный набор записей
`ДенежныеСредстваБезналичные`: проверяются активный приход, отсутствие сторно,
организация, банковский счёт, нулевое ожидание зачисления и полная сумма денег.
Без подтверждения движения приложение не сообщает об успешной оплате.

UUID поступления равен UUID заказа рынка (это разные типы документов),
маркер — `BICYCLE_PAYMENT/<UUID>`. Повтор сначала ищет тот же документ и
сверяет его поля. Уже проведённое поступление не проводится повторно.
Неопределённый результат сети требует повтора кнопки, а не нового документа.
Завершённые удалённые/изменённые поступления не заменяются новыми.

В Элементе сохраняются GUID оплаты, подтверждение, ошибка и аренда попытки.
Параллельная попытка блокируется; устаревший ответ не перезаписывает новую.
Статус ERP и банковское движение проверяются повторно фоновым опросом. Для
нового зачёта требуются закрытие и подтверждённая оплата. Ответ после дедлайна
отражается в карточке, но не изменяет зафиксированный портфель.

## Проверка реквизитов целевой ERP

OData базы 1550925 читался с предоставленными пользователем реквизитами;
`$metadata` возвращал HTTP 500. По отдельному разрешению пользователя созданы
два диагностических черновика (реализация и поступление) без проведения и
с нулевыми суммами. После чтения реквизитов оба помечены на удаление;
проверено `Posted=false`, `DeletionMark=true`, у поступления
`ПроведеноБанком=false`. Реальные поступления денег и отгрузки не проводились.

Сохранён обезличенный список полей в
`contracts/erp-order-closure-schema.json`: только имена реквизитов и полей
табличных частей, без учётных данных, контрагентов и хозяйственных сумм.
Ключ набора регистра проверен чтением существующего начального документа:
`Recorder` — строка UUID, `Recorder_Type` — полное имя типа.

## Локальные проверки

- `test_erp_order_closure.py` на Element Script 10.0.2_1 выполняет исходный
  XBSL против локального OData-имитатора: 26 сценариев, 367 запросов.
  Полная/частичная отгрузка, два товара/две реализации, расчёты по заказу и
  накладным, отсутствие складского списания, чужой заказ/организация,
  изменённый товар/цена, перепоставка, отменённая строка, непроведённый или
  удалённый документ, банковский счёт с дублем, занятый GUID, конфликт версии,
  потеря ответа закрытия/создания/проведения, многостраничное чтение, другая
  валюта, ручная оплата и отсутствие денежного движения. Повтор не создаёт
  второе поступление. Поля запроса сверяются с прочитанной схемой ERP.
- `test_market_odata.py`: существующий цикл рынка плюс исходные методы
  резервирования/подтверждения закрытия: владелец, токен, раунд, этап,
  параллельность, устаревший ответ, ошибка/повтор, фиксация по сроку. Проверены
  новые данные строк ЛК и отсутствие зачёта ручного статуса без оплаты.
- `test_background_setup.py`: подготовка баз и история до появления раундов.
- `test_erp_setup_xbsl.py`: 1255 локальных запросов подготовки без дублей.
- `xbsl-validate`: 133 YAML, 0 ошибок, 48 предупреждений о границах UI-проверки.

Это проверки исходного XBSL и реквизитов ERP. Полный сценарий с реальной
отгрузкой, проведённым банковским поступлением и интерфейсом проверяет
пользователь, как было согласовано.
