# Обмен, который инициирует игра

Элемент обращается к каждой базе ERP под сохранёнными логином и паролем этой базы. Пользователь приложения Элемента и сервисная привязка для ERP больше не требуются. Учётные данные остаются на сервере; на клиент возвращаются адрес, логин и признак сохранённого пароля.

## Настройка команды

1. В карточке команды сохраните адрес публикации ERP, организацию, логин и пароль. Здесь же доступна подготовка или чтение готовой базы через OData, с сохранением всех 15 соответствий номенклатуры.
2. В «Настройка игры → Открыть расширенные настройки игры → ERP команды» выберите команду. Укажите **«HTTP-сервис ERP для этапов и итогов»** и сохраните адрес. Он доступен для изменения до подготовки игры.
3. Если отдельный адрес не сохранён, используется адрес публикации этой команды с суффиксом `/hs/game/v1/`. Это путь нового сервиса, который нужно реализовать и опубликовать в расширении ERP. Сам стандартный OData его не создаёт.
4. Подготовьте игру. Серверное задание «ФоновыйОбменERP» запускает опрос каждые 5 секунд, независимо от открытых форм. Для каждой команды создаётся отдельное задание «ОбменКомандыERP»; недоступная база не блокирует опрос остальных команд. Пульт и диагностика читают сохранённое состояние.

Задание создаётся автоматически при обновлении приложения. Сервис запланированных заданий платформы должен быть включён и запускаться вместе с приложением. Опрос работает в подготовке, активной игре и на паузе. Для завершённых и отменённых игр доставляется только оставшаяся команда остановки; после её подтверждения опрос прекращается. Черновики, удалённые игры и неактивные команды не опрашиваются.

Повторный тик не запускает второе задание для уже опрашиваемой команды: постоянный ключ и стратегия `Отбросить` сохраняют выполняющееся задание. Если HTTP-запрос длится дольше 5 секунд, следующий опрос этой команды начинается после завершения предыдущего. Сетевые вызовы выполняются вне транзакций. Серверный обработчик использует привилегированный контекст и не требует сессии ведущего; клиентская команда синхронизации по-прежнему проверяет права ведущего.

## Разделение операций

| Канал | Операции |
|---|---|
| OData | Организации, подготовка/чтение начальных данных, цены и остатки; создание и проведение заказов клиента, включая заказы из окончательного расчёта с несколькими моделями |
| HTTP-сервис ERP | Применение подготовки игры, открытие/фиксация фаз, пауза/возобновление; получение согласованных снимков, готовности, реализаций и платежей; сложная оплата реализации и финансы после закрытия месяца |

Операции закупок и производства в режиме `basic` выполняют студенты. Для режима `automatic` сервис ERP также выполняет предусмотренные контрактом цепочки и возвращает отчёты исполнения. Итоговые деньги и прибыль по-прежнему берутся из ERP, а не вычисляются по распределённым заказам.

## Контракт сервиса ERP

[OpenAPI](../contracts/erp-pull.openapi.json) генерируется командой `python3 scripts/generate_game_contract.py` вместе с модулем схем `КонтрактERP.xbsl`. Путь сервиса задаётся в настройках команды; относительные ресурсы:

| Метод | Ресурс | Назначение |
|---|---|---|
| POST | `commands` | Выполнить или продолжить команду; ответ 200/202 с её результатом |
| POST | `state` | Только прочитать состояние и ещё не подтверждённые факты; ответ 200 |
| POST | `ack` | Подтвердить сохранённые Элементом сообщения; ответ 204 |

Используется HTTP Basic с учётной записью ERP и HTTPS. В запросе передаются `X-Game-Contract-Version: 1.0`, `Idempotency-Key` и JSON UTF-8. Перенаправления отключены. Ответ ограничен 1 МиБ, таймаут HTTP-сервиса — 15 секунд. Для долгой операции сервис возвращает `receipt.status=processing`; следующий запрос с тем же `commandId` продолжает проверку результата.

Запрос `commands`/`state` содержит:

- `context`: игра, команда, раунд, фаза, токен, версия, дедлайн и полный профиль. `phaseState` различает открытый этап (`open`), фиксацию (`freezing`), ожидание исполнения (`waiting_erp`) и закрытие (`closed`). `bindingId` отсутствует.
- `organization`: выбранная организация ERP.
- `mappings`: все 15 фактических соответствий номенклатуры этой базы.
- `orders`: подтверждённые заказы текущего раунда с исходным заданием, `allocationId`, `externalOrderId` и реальными GUID ERP. Включает заказы, созданные игроками через OData.
- `playerFinished`: заявление команды о завершении этапа. Оно не заменяет технические проверки ERP.
- `allocationReady`: окончательный расчёт раунда сохранён. До этого момента сервис не возвращает финансовые события реализации; они сохраняются в ERP для последующей доставки.
- `command`: неизменяемый конверт задания, только для `commands`.

Обязательные поля ответа: `contractVersion`, `salesEvents`, `executionEvents`. Пустые массивы допустимы. Дополнительно сервис возвращает `snapshot`, `readiness`, `receipt`, `commandId`.

Для подтверждения задания `commandId` должен совпадать с отправленным. Все вложенные сообщения сохраняют поля исходного игрового контракта: `messageId`, `gameId`, `participantId`, `roundNumber`, `gameMonth`, `phaseToken`, версии и предметные данные. Элемент повторно проверяет их принадлежность и бизнес-правила.

В `receipt.snapshotId` и `readiness.snapshotId` сервис указывает **messageId снимка из этого же ответа**. После приёма снимка Элемент подставляет свою локальную ссылку. ERP не должна знать UUID документа снимка в Элементе. Готовность без вложенного снимка не принимается.

На открытом этапе `state` возвращает актуальный `monitoring` и техническую готовность. После истечения дедлайна, на паузе или после начала фиксации новые `monitoring`/`readiness` не возвращаются. Команда `freeze_phase` возвращает `frozen` с заданными `sourceVersion` и `freezeCommandId`. `request_final_snapshot` возвращает `final`, деньги, прибыль, долги и `monthClosed`; Элемент проверяет завершение оплат и закрытие месяца.

## Повторы и согласованность

Задания сначала сохраняются в транзакции игры. Резерв отправки фиксируется отдельной транзакцией, сетевые вызовы выполняются без блокировки игры, результаты сохраняются в следующей транзакции. Пятиминутная аренда и номер попытки дополнительно защищают одно задание от повторной отправки при конкурирующих серверных вызовах. При транспортном сбое повтор разрешается через 15 секунд.

Сервис ERP хранит результат по `commandId`; повтор не создаёт второй документ. При возобновлении или ручном повторе новое транспортное задание сохраняет хозяйственные `externalOrderId`, `paymentOperationId`, `businessOperationId`. Сервис сверяет неизменяемый конверт, а не весь запрос: `context.serverTime` и текущее состояние могут измениться между попытками.

Открытие, пауза и возобновление имеют приоритет перед хозяйственными заданиями. На паузе отправляется только команда паузы. После возобновления старые не завершённые конверты отменяются; выполняются новые конверты с текущим токеном и прежними хозяйственными идентификаторами.

Отмена и окончательное завершение игры сохраняют команду `pause_game`, чтобы ERP прекратила учебные изменения. Для таких игр клиент доставляет только это завершающее задание; дальнейшее чтение состояния прекращается. Контекст задания содержит `gameState=cancelled/completed`.

Каждое сообщение имеет уникальный `messageId` и неизменяемое тело. Сервис сохраняет не подтверждённые факты и повторяет их до `ack`. Квитанция отправляется только после успешного сохранения ответа в Элементе. Потеря квитанции приводит к повторному чтению; журнал Элемента возвращает прежний результат. Квитанция не удаляет журнал исполнения хозяйственных операций ERP.

Факты продаж/исполнения принимаются перед итоговым снимком. Если любое сообщение не прошло проверку, весь ответ откатывается и `ack` не отправляется. При смене версии игры или токена во время сетевого вызова ответ не применяется и не подтверждается; исходное задание сохраняется для проверки/повтора. Сообщения об ошибках связи показываются в пульте, не стирая ранее сохранённый снимок; они блокируют переход до успешного обмена.

Для OData используются устойчивые идентификаторы заказов и строк. Повтор сначала ищет ранее созданный заказ и проверяет состав, организацию, количества и цены. Проведение проверяется отдельным чтением `Posted`; расчётное создание заказа не считается фактом отгрузки или оплаты.

## Переход со старой схемы

Назначения сервисных пользователей скрыты из настроек ERP команды; исторические записи не удаляются. Старый входящий API Элемента `/api/game/v1/bindings/...` возвращает `ERP_PULL_MODE` и не применяет данные, чтобы два транспорта не меняли одну игру одновременно. [Старый контракт](erp-http.md) оставлен для истории.

Нужно реализовать новый сервис в расширении ERP по опубликованному контракту. В этом репозитории находятся исходники Элемента; реализация сервиса ERP сюда не входит. До публикации этого сервиса пульт показывает ошибку связи и не подтверждает подготовку/фиксацию.

## Проверки

`scripts/test_erp_pull.py --runtime <дистрибутив Element Script 10.0>` исполняет оригинальные методы проверки схем, подстановки снимка, формирования строк OData и HTTP-клиента. Локальный тестовый ERP проверяет авторизацию, заголовки, обработку HTTP-ошибок, неверного JSON и ограничения размера. Реальные базы не изменяются.

Проверка метаданных и эти тесты не заменяют компиляцию всего приложения и прогон фаз на опубликованной ERP.
