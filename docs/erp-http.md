# HTTP-обмен с расширением ERP — контракт 1.0

Серверная сторона реализована в исходниках приложения Элемента по приложению В `ТЗ_Расширение_ERP.docx`. Расширение ERP инициирует запросы: получает контекст и команды, отправляет снимки и факты. Элемент не обращается к ERP по OData для выполнения этого протокола.

**Статус:** HTTP-контракт сохранён в окончательной сборке `1.0-31`; [новые административные экраны](admin-panel.md). Локальные проверки пройдены; полный проект прошёл нативную компиляцию и опубликован в сборке `1.0-27` 8 октября 2026 года. Задача обновления `Completed`, приложение `Running`, ошибок и текущей задачи нет. Все семь маршрутов возвращают `403` без аутентификации. Авторизованный обмен, транзакции и права ещё не проходили интеграционную проверку с ERP. [Подробности публикации](deployment.md).

## Адреса и авторизация

Базовый адрес: `https://app-312909758.1cmycloud.com/applications/game-dev/api/game/v1`. В YAML задан `/game/v1`, поскольку `/api` добавляет платформа.

Все семь маршрутов доступны только аутентифицированному пользователю, назначенному конкретной сервисной привязке. Администратор не получает доступ к чужому bindingId через HTTP. Токен выдаётся механизмом аутентификации приложения Элемента; Console API token для управления облачными приложениями не заменяет этот служебный токен.

| Метод | Путь относительно базового адреса | Назначение |
|---|---|---|
| GET | `/bindings/{bindingId}/context` | Текущие игра, команда, раунд, месяц, дата документов, фаза, токен, версия состояния, дедлайн, неизменные настройки и их SHA-256 |
| GET | `/bindings/{bindingId}/commands` | Очередь с непрерывным курсором подтверждений |
| POST | `/bindings/{bindingId}/snapshots` | Полный согласованный снимок monitoring, frozen или final |
| POST | `/bindings/{bindingId}/readiness` | Готовность или её отзыв со ссылкой на принятый снимок |
| POST | `/bindings/{bindingId}/commands/{commandId}/receipt` | processing, completed или failed конкретной команды |
| POST | `/bindings/{bindingId}/sales-events` | Полная версия реализации и отнесённых на неё платежей |
| POST | `/bindings/{bindingId}/execution-events` | Состояние автоматической цепочки; в basic возвращается MODE_MISMATCH |

Обязательные заголовки:

```http
Authorization: Bearer <служебный токен приложения>
X-Game-Contract-Version: 1.0
```

Для POST дополнительно:

```http
Content-Type: application/json; charset=utf-8
Idempotency-Key: <тот же UUID, что messageId в JSON>
```

Тело — UTF-8 JSON размером не более 1 МиБ без Content-Encoding. Деньги передаются строками с двумя знаками, количества — строками с максимум шестью знаками; количество велосипедов и номера версий — целые числа. GUID — строчные, ненулевые. Неизвестные поля и недопустимые null отклоняются.

OpenAPI со всеми полями и ограничениями: [`game-api.openapi.json`](../contracts/game-api.openapi.json). Версия `0.1.0-design` заменена несовместимым нормативным контрактом `1.0`.

## Настройка обычной игры

1. Создайте обычную игру и участников, задайте сценарий. В каждой учебной фазе сценария нужен положительный срок.
2. В форме **«Доступ к игре»** выберите игру и нажмите **«Заполнить пример профиля»**. Проверьте выбранные месяцы, executionMode, priceFixation, налоговый режим и диапазоны цен. Число раундов, фиксация и границы цен должны совпадать со сценарием. Сохраните профиль до подготовки игры.
3. Пример задаёт basic, четыре производственных раунда и календарь январь–май 2027 года. Ведущий должен выбрать нужный начальный месяц. В календаре есть раунд 0, месяцы последовательны, даты документов — 15-е число каждого месяца. После подготовки профиль неизменяем.
4. Назначьте каждому участнику своё **подключение ERP** в его карточке. В существующей форме подключения хранятся сведения о базе; пароли не передаются через игровой HTTP API.
5. В форме доступа выберите команду, нажмите **«Загрузить соответствия команды»** и заполните таблицу **соответствий ERP** (импорт JSON также сохранён): реальные refKey всех 15 позиций, characteristicId при наличии, единицу ERP и коэффициент «единиц ERP в одной игровой единице». Сохраните соответствия. Пустые GUID в шаблоне — поля для заполнения, а не рабочие значения. Если characteristicId указан в соответствиях, ERP передаёт его в каждой соответствующей строке balances.
6. В форме доступа выберите участника ERP и служебного пользователя, нажмите **«Назначить сервис ERP»**. Сообщение показывает bindingId. Один активный пользователь соответствует одной игровой области, у участника одна активная привязка.
7. Передайте расширению базовый URL, bindingId и служебные реквизиты аутентификации. Нажмите **«Подготовить игру»** в пульте. Контекст появляется после подготовки; ERP получает prepare_game. Запуск игры ждёт успешную подготовку всех участников.

Шаблоны: [`erp-profile.example.json`](../contracts/erp-profile.example.json), [`erp-mappings.template.json`](../contracts/erp-mappings.template.json). При сохранении профиля settingsHash пересчитывается по каноническому JSON настроек. Для подготовленной ERP начальные количества, себестоимость, деньги и продажные цены задаются по фактическим данным базы, а не сверяются с числовыми значениями примера. Сохраняются проверки схемы, 26 уникальных остатков, включая нули, единиц, четырёх моделей, положительных продажных цен и валюты. Сохранение профиля добавляет отсутствующие позиции игрового каталога, без выдумывания GUID ERP. Начальную цену необходимо принять до подготовки игры; готовую ERP нельзя сбрасывать начальным пакетом шаблона.

В раунде 0 цена `frozen` должна точно совпадать с принятой начальной ценой ERP. При расчёте стартового рынка эта цена включается в допустимый диапазон вычисления; референтная цена и формула спроса сохраняются. В последующих раундах действуют утверждённые границы сценария. [Проверка изменения](market-erp.md).

## Команды и порядок выполнения

Выходные команды: prepare_game, open_phase, freeze_phase, create_customer_order, pay_realization, request_final_snapshot, pause_game, resume_game. Их payload определён в OpenAPI; commandId и хозяйственные идентификаторы заказа/оплаты назначает Элемент.

`GET commands` требует gameId; afterSequence по умолчанию 0, limit по умолчанию 20, диапазон limit 1–100. Переданный курсор не позволяет пропустить ранее неподтверждённую команду. acknowledgedThroughSequence двигается только через непрерывный ряд completed/failed; processing его не продвигает. Последняя ожидающая pause_game/resume_game резервирует место в каждой странице; при limit=1 выдаётся управляющая команда.

В обычной игре кнопка перехода сначала закрывает приём готовности и выдаёт freeze_phase. Следующее нажатие ждёт completed и принятый frozen. В продажах затем фиксируется рынок, выдаются заказы и игра остаётся в ожидании ERP. В анализ переходят после подтверждённых заказов, фактов продаж и оплат; в automatic также требуется завершение цепочек. Анализ выдаёт request_final_snapshot, итог принимается только после закрытия месяца и сверки оплат.

Замороженное предложение не заменяется monitoring. При after_planning цены продажи проверяются по сохранённой фиксации планирования. Для initial_sales цена устанавливается до первой фиксации независимо от настройки.

Расширение должно хранить команду и её хозяйственный результат до подтверждения. При паузе не начинаются новые движения. Возобновление выдаёт новый токен; хозяйственные operationId, businessOperationId, externalOrderId и paymentOperationId продолжают прежние операции. Невыполненные заказы/оплаты могут поступить повторно с новым commandId и тем же хозяйственным ключом. Это не разрешение создать второй документ. Старые команды завершаются подтверждением их прежнего результата либо failed с причиной устаревшей фазы.

Кнопка **«Повторить ошибочные задания ERP»** выдаёт новую транспортную команду после исправления причины ошибки, сохраняя хозяйственные идентификаторы заказа и оплаты. Терминальное подтверждение старой команды остаётся в истории. Фиксация при повторе получает новую sourceVersion.

## Повторы, факты и деньги

Успешный POST возвращает HTTP 200:

```json
{
  "contractVersion": "1.0",
  "messageId": "00000000-0000-4000-8000-000000000100",
  "resourceId": "00000000-0000-4000-8000-000000000020",
  "replayed": false
}
```

Повторяют тот же метод, путь, messageId и **неизменные байты тела**. Изменение форматирования тоже является изменением тела и даёт IDEMPOTENCY_CONFLICT. Совпавший повтор возвращает прежний resourceId и replayed=true до проверки сменившейся фазы или дедлайна. Журнал сообщений, факты, подтверждение и выдача связанных команд записываются в одной транзакции под блокировкой игры.

Факты реализации принимаются как полное состояние: новые версии заменяют предыдущее, старые возвращают STALE_EVENT_VERSION, одна версия с разными предметными данными — EVENT_VERSION_CONFLICT. Платёж не исчезает из массива: отменённый передаётся как reversed. Суммарная отгрузка по всем реализациям не превышает заказ, цена соответствует рынку, lineAmount сверяется с налоговым профилем. Элемент выдаёт оплату только на непогашенную сумму с учётом уже выданных платежных команд.

Поздние факты и receipt допускаются в исходной подтверждённой игровой области после смены фазы/срока. Это не открывает новые хозяйственные действия. Новый снимок со старым токеном отклоняется; разрешён точный транспортный повтор уже принятого сообщения. Изменение финансового факта после final снимает подтверждение результатов затронутого и последующих периодов и отменяет публикацию рейтинга. Для повторной публикации нужна сверка; сервер не пересчитывает cash из рыночной выручки. В сборке `1.0-31` добавлена ручная административная сверка по свежему финальному снимку ERP: права ведущего, новые идентификаторы, порядок периодов, оплаты и аудит. Обычные HTTP-запросы по-прежнему проверяют текущую фазу; [процедура и границы проверки](admin-panel.md).

## Вызовы из расширения

```sh
curl --fail-with-body \
  -H "Authorization: Bearer $ERP_SERVICE_TOKEN" \
  -H 'X-Game-Contract-Version: 1.0' \
  "$GAME_API_URL/bindings/$BINDING_ID/context"

curl --fail-with-body --get \
  -H "Authorization: Bearer $ERP_SERVICE_TOKEN" \
  -H 'X-Game-Contract-Version: 1.0' \
  --data-urlencode "gameId=$GAME_ID" \
  --data-urlencode 'afterSequence=0' \
  --data-urlencode 'limit=20' \
  "$GAME_API_URL/bindings/$BINDING_ID/commands"

curl --fail-with-body \
  -H "Authorization: Bearer $ERP_SERVICE_TOKEN" \
  -H 'X-Game-Contract-Version: 1.0' \
  -H 'Content-Type: application/json; charset=utf-8' \
  -H "Idempotency-Key: $MESSAGE_ID" \
  --data-binary @snapshot.json \
  "$GAME_API_URL/bindings/$BINDING_ID/snapshots"
```

snapshot.json содержит поля текущего контекста и полный пакет ERP. Примеры из исходного ТЗ находятся в `contracts/erp-spec-tables.json`, раздел examples; демонстрационные UUID заменяются фактическими. GAME_API_URL включает `/api/game/v1`, MESSAGE_ID совпадает с полем JSON. Секреты в репозиторий не сохраняются.

Ошибка содержит contractVersion, code, message, correlationId; ошибки 422 также details. 400 — JSON; 401 — аутентификация; 403 — область привязки; 404 — ресурс; 405 — метод с Allow; 409 — версия/фаза/повтор; 413 — размер; 422 — схема/соответствия/возможности; 500 — внутренний сбой. Платформа может вернуть собственное тело ошибки, если отклонила запрос до вызова обработчика.

## Проверки и границы

Пройдены: 93 YAML, 87 объектов, 402 уникальных UUID, согласованность 44 XBSL-файлов, валидатор метаданных без ошибок и git diff --check. Валидатор сообщает 32 предупреждения о UI/контейнерах вне его покрытия.

50 существующих регрессионных тестов и один нативный тестовый запуск прошли. Последний компилирует исходные функции протокола/схем/очереди в Element Script 10.0.2-1, выполняет 65 положительных и отрицательных случаев из нормативных примеров, проверяет канонический JSON/SHA-256, совпадение hash профиля с Python, календарь, суммы/округление НДС и очередь с разрывом курсора и приоритетом управления.

```sh
python3 scripts/generate_game_contract.py
python3 scripts/check_metadata.py
python3 scripts/check_sources.py
python3 -m unittest discover -s scripts -p 'test_*.py'
```

Для нативного теста задайте ELEMENT_SCRIPT_HOME — каталог установленного Element Script с lib/ и config/, ELEMENT_SCRIPT_JAVA — Java 17. Без runtime этот тест явно пропускается. Генерация OpenAPI воспроизводится по сохранённым таблицам ТЗ; для повторного извлечения из Word используйте `--spec /путь/ТЗ_Расширение_ERP.docx`.

Полная компиляция приложения выполнена. На этапе подключения ERP требуется интеграционная проверка: служебные пользователи, авторизованные запросы ко всем семи маршрутам, повторные POST и конкуренция с ведущим, запись/отмена реализаций и платежей, pause/resume, automatic и конечная сверка с типовыми документами ERP. Проверка чистых функций и ответов без аутентификации не подтверждает эти сценарии.
