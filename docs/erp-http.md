# HTTP-обмен с расширением ERP — контракт 1.0

Серверная сторона реализована в исходниках приложения Элемента по приложению В `ТЗ_Расширение_ERP.docx`. Расширение ERP инициирует запросы: получает контекст и команды, отправляет снимки и факты. Элемент не обращается к ERP по OData для выполнения этого протокола.

## Адреса и авторизация

Базовый адрес: `https://app-312909758.1cmycloud.com/applications/game-dev/api/game/v1`. В YAML задан `/game/v1`, поскольку `/api` добавляет платформа.

Все семь маршрутов доступны только аутентифицированному пользователю, назначенному конкретной сервисной привязке. Администратор не получает доступ к чужому bindingId через HTTP. Токен выдаётся механизмом аутентификации приложения Элемента; Console API token для управления облачными приложениями не заменяет этот служебный токен.

| Метод | Путь относительно базового адреса | Назначение |
|---|---|---|
| GET | `/bindings/{bindingId}/context` | Текущие игра, команда, раунд, месяц, дата документов, фаза, токен, версия состояния, дедлайн, неизменные настройки и их SHA-256 |
| GET | `/bindings/{bindingId}/commands` | Очередь с непрерывным курсором подтверждений |
| POST | `/bindings/{bindingId}/snapshots` | Полный согласованный снимок monitoring, frozen или final |
| POST | `/bindings/{bindingId}/readiness` | Готовность или её отзыв со ссылкой на принятый снимок |
| POST | `/bindings/{bindingId}/commands/{commandId}/receipt` | processing, completed или failed конкретной команды |
| POST | `/bindings/{bindingId}/sales-events` | Полная версия реализации и отнесённых на неё платежей |
| POST | `/bindings/{bindingId}/execution-events` | Состояние автоматической цепочки; в basic возвращается MODE_MISMATCH |

Обязательные заголовки:

```http
Authorization: Bearer <служебный токен приложения>
X-Game-Contract-Version: 1.0
```

Для POST дополнительно:

```http
Content-Type: application/json; charset=utf-8
Idempotency-Key: <тот же UUID, что messageId в JSON>
```

Тело — UTF-8 JSON размером не более 1 МиБ без Content-Encoding. Деньги передаются строками с двумя знаками, количества — строками с максимум шестью знаками; количество велосипедов и номера версий — целые числа. GUID — строчные, ненулевые. Неизвестные поля и недопустимые null отклоняются.

OpenAPI со всеми полями и ограничениями: [`game-api.openapi.json`](../contracts/game-api.openapi.json). Версия `0.1.0-design` заменена несовместимым нормативным контрактом `1.0`.

## Настройка игры

Сохраните сценарий и профиль: календарь от раунда 0, налоговый режим, границы цен и фактический начальный пакет ERP. Для каждой команды задайте подключение, соответствия всех 15 позиций и служебную привязку пользователя ERP. Формат профиля описан в [контракте](../contracts/game-api.openapi.json); [шаблон соответствий](../contracts/erp-mappings.template.json) заполняется реальными идентификаторами ERP.

В пульте подготовьте игру. Расширение получает `prepare_game`; запуск ждёт подтверждений всех команд. После подготовки настройки фиксируются. Начальные цены, остатки, себестоимость и деньги берутся из ERP.

## Команды и порядок выполнения

Выходные команды: prepare_game, open_phase, freeze_phase, create_customer_order, pay_realization, request_final_snapshot, pause_game, resume_game. Их payload определён в OpenAPI; commandId и хозяйственные идентификаторы заказа/оплаты назначает Элемент.

`GET commands` требует gameId; afterSequence по умолчанию 0, limit по умолчанию 20, диапазон limit 1–100. Переданный курсор не позволяет пропустить ранее неподтверждённую команду. acknowledgedThroughSequence двигается только через непрерывный ряд completed/failed; processing его не продвигает. Последняя ожидающая pause_game/resume_game резервирует место в каждой странице; при limit=1 выдаётся управляющая команда.

В игре кнопка перехода сначала закрывает приём готовности и выдаёт freeze_phase. Следующее нажатие ждёт completed и принятый frozen. В продажах затем фиксируется рынок, выдаются заказы и игра остаётся в ожидании ERP. В анализ переходят после подтверждённых заказов, фактов продаж и оплат; в automatic также требуется завершение цепочек. Анализ выдаёт request_final_snapshot, итог принимается только после закрытия месяца и сверки оплат.

Замороженное предложение не заменяется monitoring. При after_planning цены продажи проверяются по сохранённой фиксации планирования. Для initial_sales цена устанавливается до первой фиксации независимо от настройки.

Расширение должно хранить команду и её хозяйственный результат до подтверждения. При паузе не начинаются новые движения. Возобновление выдаёт новый токен; хозяйственные operationId, businessOperationId, externalOrderId и paymentOperationId продолжают прежние операции. Невыполненные заказы/оплаты могут поступить повторно с новым commandId и тем же хозяйственным ключом. Это не разрешение создать второй документ. Старые команды завершаются подтверждением их прежнего результата либо failed с причиной устаревшей фазы.

Кнопка **«Повторить ошибочные задания ERP»** выдаёт новую транспортную команду после исправления причины ошибки, сохраняя хозяйственные идентификаторы заказа и оплаты. Терминальное подтверждение старой команды остаётся в истории. Фиксация при повторе получает новую sourceVersion.

## Повторы, факты и деньги

Успешный POST возвращает HTTP 200 и поля `contractVersion`, `messageId`, `resourceId`, `replayed`. Идентификаторы относятся к принятому сообщению и сохранённому ресурсу.

Повторяют тот же метод, путь, messageId и **неизменные байты тела**. Изменение форматирования тоже является изменением тела и даёт IDEMPOTENCY_CONFLICT. Совпавший повтор возвращает прежний resourceId и replayed=true до проверки сменившейся фазы или дедлайна. Журнал сообщений, факты, подтверждение и выдача связанных команд записываются в одной транзакции под блокировкой игры.

Факты реализации принимаются как полное состояние: новые версии заменяют предыдущее, старые возвращают STALE_EVENT_VERSION, одна версия с разными предметными данными — EVENT_VERSION_CONFLICT. Платёж не исчезает из массива: отменённый передаётся как reversed. Суммарная отгрузка по всем реализациям не превышает заказ, цена соответствует рынку, lineAmount сверяется с налоговым профилем. Элемент выдаёт оплату только на непогашенную сумму с учётом уже выданных платежных команд.

Поздние факты и receipt допускаются в исходной подтверждённой игровой области после смены фазы/срока. Это не открывает новые хозяйственные действия. Новый снимок со старым токеном отклоняется; разрешён точный транспортный повтор уже принятого сообщения. Изменение финансового факта после final снимает подтверждение результатов затронутого и последующих периодов и отменяет публикацию рейтинга. Для повторной публикации нужна сверка; сервер не пересчитывает cash из рыночной выручки. Реализована ручная административная сверка по свежему финальному снимку ERP: права ведущего, новые идентификаторы, порядок периодов, оплаты и аудит. Обычные HTTP-запросы по-прежнему проверяют текущую фазу; [процедура и границы проверки](admin-panel.md).
