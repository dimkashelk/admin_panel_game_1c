# Модель данных Элемента

Метаданные для версии 10.0 созданы в существующем проекте `dimkashelk/Игра`. YAML, UUID и ссылки прошли локальные проверки; бизнес-ограничения и обработчики записи из этого документа ещё предстоит реализовать и проверить компилятором. Перечень созданных объектов и команды проверки находятся в [описании каркаса](metadata.md).

## Правила хранения

- Все игровые объекты относятся к одной игре; в запросах явно фильтруются игра и участник.
- Деньги и цены хранятся как `Число` с двумя десятичными знаками; коэффициенты — с достаточной точностью для расчёта. Велосипеды считаются в целых штуках, сырьё может иметь дробное количество.
- Время события — `Момент`. Игровой период — отдельная дата начала месяца.
- Идентификаторы сообщений и внешних документов не заменяются названиями объектов.
- Ссылочный реквизит в YAML имеет тип вида `Игры.Ссылка?`; обязательность связи проверяется при записи и переходе состояния.
- Перечисление либо nullable, либо имеет явное значение по умолчанию. UUID получают объект и пользовательские реквизиты; системные поля описываются по правилам своего типа.
- У исторических ссылочных измерений регистра задаётся `Ведущее: Ложь`: удаление справочника не должно каскадно уничтожить расчёты. Использованные игры и настройки не удаляются физически.

## Независимые регистры сведений

Все перечисленные регистры непериодические: номер раунда, токен или номер сообщения входят в явный ключ. Прикладная история не строится на случайном совпадении временных меток.

| Имя | Измерения — уникальный ключ | Ресурсы и реквизиты |
|---|---|---|
| `НазначенияПользователей` | Пользователь, Игра, ПрикладнаяРоль | Активно |
| `ПривязкиСервисовERP` | СервисныйПользователь, Участник | Активно; связь дополнительно ограничена подключением |
| `СоответствияERP` | Подключение, НоменклатураИгры | EntitySet, RefKey, КлючХарактеристики, ЕдиницаERP, КоэффициентПересчета |
| `СостоянияУчастников` | Участник, Раунд, ТокенФазы | Готов, ПоследнийСнимок, ВремяСвязи, Ошибка, Версия |
| `ПринятыеСообщения` | Подключение, ИдСообщения | ХешЗапроса, Результат, КодОтвета, МоментПриема |
| `ИсполнениеПродаж` | Расчет, Участник, Продукт, ИдРеализацииERP | Отгружено, Цена, СуммаРеализации, Оплачено, ВерсияФакта |
| `ПлатежиПродаж` | Расчет, Участник, Продукт, ИдРеализацииERP, ИдПлатежаERP | СуммаПлатежа, ВерсияФакта, МоментПлатежа |
| `РезультатыРаундов` | Раунд, Участник | ФинальныйСнимок, ДеньгиНачало, ДеньгиКонец, ВыручкаФакт, Прибыль, Долги, ОстаткиГП, ЗакрытиеМесяцаПодтверждено |

`ИсполнениеПродаж` хранит обновляемое состояние конкретной реализации с монотонной `ВерсияФакта`; повтор события возвращает прежний ответ. Несколько платежей одной реализации хранятся в `ПлатежиПродаж`, где идентификатор платежа входит в ключ. `Оплачено` — агрегат, который серверная обработка должна пересчитывать атомарно по принятым платежам. До обследования ERP не предполагается связь «один документ — один платёж».

## Ключи и конкурентные изменения

Уникальность ключей регистров используется для дедупликации. Уникальные сочетания справочников проверяются сервером под блокировкой соответствующей игры или подключения; один обычный индекс не считается гарантией уникальности.

Для игры сериализуются переход фазы, фиксация снимков и финализация расчёта. Обмен с сетью выполняется за пределами блокировки. Для очереди сериализуются выдача очередного номера и изменение статуса по одному участнику. Порядок захвата нескольких блокировок фиксируется заранее.

Номер раунда не глобален: всегда используется вместе со ссылкой на игру. Номенклатура ERP сопоставляется по GUID и характеристике, а не по похожему названию; комплект колёс и штуки колёс требуют явного коэффициента пересчёта.

## Серверные модули и контракты

| Подсистема | Элемент | Назначение |
|---|---|---|
| Данные | `ПроверкиДанных`, ОбщийМодуль | Локальные инварианты метаданных |
| Рынок | `РасчетРынка`, ОбщийМодуль, Сервер | Чистый расчёт по входному снимку без сетевых вызовов |
| Обмен | `ШлюзERP`, КонтрактСервиса | Нормализованные возможности проверки, чтения и исполнения |
| Обмен | `ШлюзHttpERP`, `ШлюзODataERP`, ОбщийМодуль, Сервер | Конкретные реализации транспорта |
| Обмен | `ИгровойHttpСервис`, HttpСервис | Приём сообщений и выдача команд адаптеру ERP |
| Обмен | `ОчередьОбмена`, ОбщийМодуль, Сервер | Повторы, дедупликация, последовательность |
| Управление | `УправлениеИгрой`, ОбщийМодуль, Сервер | Переходы фаз и согласование результатов |
| Аналитика | `РезультатыИгры`, ОбщийМодуль, Сервер | Доступные пользователю результаты |

Для нескольких реализаций `ШлюзERP` используется множественный контракт; реализация выбирается по режиму подключения. Каждая реализация сообщает свои возможности. Отсутствие функции фиксации или безопасного исполнения команды блокирует переход соответствующей фазы, а не скрывается за общим статусом «подключено».

## Проверки при записи и запуске

1. В сценарии есть четыре продукта, каждый ровно один раз; цены положительны, минимум не выше референтной цены, референтная не выше максимума.
2. Спрос, тренд и коэффициенты неотрицательны; количество раундов положительно.
3. У участников нет пересечения игровых областей; каждая область имеет полное соответствие продукции и нужных ресурсов.
4. Принятие готовности ссылается на снимок того же участника, раунда и токена.
5. Расчётный заказ не превышает зафиксированное доступное количество; фактическая отгрузка не превышает заказ без отдельного события исправления.
6. Итоговые деньги пришли из ERP; снимки с отсутствующими показателями не дают нулевой результат и не участвуют в финальном рейтинге.
