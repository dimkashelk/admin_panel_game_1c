# Каркас метаданных

Разработка ведётся в ветке `dev`. Используется существующий проект `dimkashelk/Игра`, режим совместимости `10.0`, версия `1.0`. Идентификатор проекта сохранён: `01a11176-4f13-7a4b-868d-0b73131db732`.

## Подсистемы

| Подсистема | Использование | Состояние |
|---|---|---|
| Данные | — | Справочники, документы, перечисления и независимые регистры |
| Рынок | Данные | Чистый расчёт двух алгоритмов и предварительная проверка |
| Обмен | Данные | Подготовлена подсистема для адаптеров и обработки очереди |
| Аналитика | Данные | Рейтинг, финансовые итоги и форма результатов |
| Управление | Данные, Рынок, Обмен, Аналитика | Управление фазами, подготовка и формы приложения |

Типы данных имеют видимость `ВПроекте`, чтобы будущие модули и формы могли импортировать `Данные`. Все объекты хранения расположены в одной подсистеме: между ними не нужны межподсистемные импорты.

Снимки, расчёты и события из проектной модели реализованы документами: у них есть системные дата и номер, а для точного времени — отдельные реквизиты `Момент`. Закупки, выпуск и реализации по-прежнему учитываются документами ERP.

У сценария и игры по четыре табличные части настроек с одинаковой структурой и разными UUID. Копирование и фиксация настроек реализованы в `УправлениеИгрой`. Добавлены признаки демонстрационной игры и опубликованных результатов, контекст RLS и отпечаток замороженных табличных настроек. Снимок содержит предложения, остатки и документы ERP; расчёт — источники, спрос продуктов и распределение заказов.

Деньги и цены имеют два десятичных знака, количество велосипедов — целочисленное, количество материалов — четыре знака, коэффициенты — восемь. Отрицательные денежные остатки и прибыль допускаются. У обязательных перечислений указаны значения по умолчанию.

В YAML значение перечисления по умолчанию записывается именем элемента, например `Черновик`; запись `СостоянияИгры.Черновик` применяется в XBSL, но не в этом свойстве YAML. Строковые реквизиты ограничены максимумом 1000 символов, который проверяет компилятор целевой платформы. Тексты описаний, ошибок и JSON-заготовок пока также ограничены 1000 символами. До реализации обмена нужно выбрать отдельное хранение больших тел сообщений; обрезать payload до допустимой длины нельзя.

`ПодключенияERP` содержит адреса HTTP и OData и идентификатор секрета `СсылкаНаСекрет`; пароли и токены в метаданных не хранятся. Механизм разрешения этого идентификатора будет реализован в адаптере.

Платежи выделены в `ПлатежиПродаж`: одна реализация может иметь несколько платежей. `Оплачено` в `ИсполнениеПродаж` — агрегат, который `ФактыПродаж` обновляет по полному состоянию принятых платежей в одной транзакции с учётом версий фактов. Доставка реальных фактов из ERP отложена.

Индексы ускоряют поиск игры, участника, раунда и команды. Дополнительные пространства блокировок подготовлены для назначения участников, раундов, окончательных расчётов и очереди. Индекс сам по себе не обеспечивает уникальность пары или идентификатора операции; серверные обработчики и команды реализуют проверки и блокировки игры, кодов и версий сценариев. Их конкурентное поведение ещё требует проверки в runtime.

Для справочников и документов выбран режим `ПометкаУдаления`. Ссылочные измерения независимых регистров имеют `Ведущее: Ложь`; удаление объекта не должно каскадно стирать игровую историю.

## Доступ и интерфейс

`КонтрольДоступа` задан явно. Изменение хранимых объектов доступно администраторам; ведущие используют авторизованные серверные команды. Номенклатуру и сценарии читают аутентифицированные пользователи. Игры, участники, раунды, снимки, расчёты и события имеют RLS по ведущим конкретной игры. Наблюдатель получает только опубликованные показатели через сервис аналитики. Доступ сервисов ERP пока не включён.

Созданы объектные формы и списки, мастер, пульт, предварительный рынок, рейтинг, назначения прав, главная и явная навигация. Всего 25 компонентов. Новые общие модули и структуры описаны в [карте реализации](development.md). Списки документов истории предназначены для чтения; сервер запрещает перезапись и удаление принятой истории.

## Проверка

Для Python 3.10+ установите зависимости из `requirements-dev.txt`, затем из корня репозитория выполните:

```bash
python3 scripts/check_metadata.py
python3 scripts/check_sources.py
python3 scripts/test_xbsl_logic.py
python3 "$HOME/.codex/skills/xbsl-validate/scripts/validate.py" dimkashelk/Игра
```

Первая команда проверяет ссылки, UUID, значения перечислений, поля индексов и блокировок, отсутствие циклов зависимостей и структуру копий настроек. Вторая проверяет YAML по установленным навыкам Элемента. Предупреждения `coverage.out_of_scope` для проекта и подсистем означают, что эти контейнеры требуют отдельной проверки.

Текущие 79 YAML прошли локальные проверки. 31 предупреждение `coverage.out_of_scope` относится к 25 UI-компонентам и 6 контейнерам, не покрытым валидатором. Дополнительно прошли проверка согласованности 31 XBSL-файла и 14 тестов чистой логики. Новые исходники не скомпилированы на платформе; эти проверки не подтверждают работу UI, БД, RLS и транзакций.

Компиляция и применение прежней сборки `1.0-4` относятся только к каркасу. [Сведения о том деплое](deployment.md). Обмен с ERP остаётся отложенным этапом.
